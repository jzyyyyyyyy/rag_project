## 1. 项目背景与意义

### 1.1 研究背景

近年来，以 GPT、DeepSeek 为代表的大语言模型（LLM）在自然语言处理领域取得了突破性进展，展现出强大的文本生成、逻辑推理和知识问答能力。然而，大语言模型在实际应用中仍存在两个核心局限性：

**（1）知识截止问题**：大模型的知识来源于训练数据，训练完成后其内部知识便固定下来，无法获取训练截止日期之后的新知识。例如，模型无法回答"2024 年巴黎奥运会女子单打网球冠军是谁"这类时效性问题。

**（2）幻觉问题**：大模型在面对超出其知识范围的问题时，往往会编造看似合理但实际错误的答案，即所谓的"幻觉"（Hallucination）现象。例如，模型可能虚构某个人物的背景信息。

针对上述问题，业界主要有两种解决方案：一是模型微调（Fine-tuning），二是基于本地知识库的检索增强生成（RAG）。

模型微调虽然可以提升模型在特定领域的适应性，但存在数据准备成本高、知识更新时效性差、技术门槛高等问题，并不适合所有场景。相比之下，RAG 技术无需重新训练模型，通过外接知识库的方式即可让大模型获得最新、最专业的知识，具有成本低、更新快、可溯源等显著优势，成为当前大模型应用落地的主流技术方案。

### 1.2 项目意义

本项目基于 RAG 技术构建一个完整的知识库智能问答系统，具有以下意义：

1. **技术实践意义**：完整复现 RAG 从文档预处理、文本分段、向量化、向量存储到检索问答的全流程，深入理解检索增强生成的核心原理与工程实现。
2. **应用价值**：系统可直接用于课程答疑、文档智能检索、企业内部知识库等实际场景，提升信息获取效率。
3. **教学示范意义**：基于课程讲授的 LangChain 框架和 RAG 原理进行工程化实现，为同类项目提供可参考的完整案例。

## 2. RAG 技术原理

### 2.1 大语言模型的局限性

大语言模型包含的是**参数化知识**，即知识以神经网络参数的形式存储在模型内部。这种知识表示方式虽然能够对一般指令作出响应，但存在固有缺陷：

- **知识截止**：模型训练完成后，内部知识不再更新，无法回答时效性问题。
- **幻觉问题**：对于未知问题，模型倾向于生成流畅但错误的回答，缺乏事实依据。
- **隐私风险**：将敏感数据用于模型微调可能导致信息泄露。
- **更新成本高**：每次知识更新都需要重新训练或微调模型，耗时耗力。

### 2.2 RAG 的定义与核心思想

**检索增强生成（Retrieval-Augmented Generation，RAG）**是一种结合了信息检索与大语言模型的技术方案。

**核心思想**：在生成答案之前，先从外部知识库中检索与用户问题相关的信息，再将检索结果与用户输入结合，指导生成模型输出更可靠的回答。

具体而言，就是利用已有的文档等资料生成向量知识库，在提问时结合从库中检索到的内容一起输入大模型，让其回答结果更加准确。RAG 结合了信息检索和大模型技术，旨在提升模型生成内容的准确性和相关性，被称为"通用的微调秘方"。

### 2.3 RAG 的完整工作流程

RAG 系统的完整流程分为**离线建库**和**在线问答**两个阶段，共包含以下步骤：

**离线建库阶段：**
1. 文档预处理：将各类文档（PDF、Word、网页等）进行加载、清洗和过滤。
2. 文本分段：将长文档按一定规则切分成多个较小的、语义相对独立的文本片段（Chunk）。
3. 文本向量化：将每个文本片段发送给嵌入模型（Embedding Model），转换为固定长度的语义向量。
4. 向量存储：将所有向量及其对应的原文片段统一存入向量数据库（即知识库）。

**在线问答阶段：**
5. 查询向量化：用户提问时，将用户问题发送给同一个嵌入模型，转换为查询向量。
6. 相似度检索：将查询向量与知识库中的所有向量进行相似度比较，找出最匹配的 Top-K 个文本片段。
7. Prompt 拼接：将检索到的原文片段与用户问题组合成结构化的 Prompt。
8. 大模型生成：将 Prompt 输入大语言模型，由模型基于检索内容整理生成最终答案。
9. 结果返回：将答案返回给用户，同时可附带来源引用，便于核实。

在后台，嵌入模型可以不断创建并更新知识库，实现知识的实时补充。

### 2.4 RAG 技术的特点与优势

RAG 技术具有以下四个核心特点：

| 特点 | 说明 |
|------|------|
| **保护数据隐私** | 业务知识保存在本地向量库中，无需上传给大模型训练，减少信息泄露风险 |
| **减少模型幻觉** | 回答基于检索到的真实业务知识，大幅降低模型胡说八道的概率 |
| **实时知识补充** | 知识库可随时更新，模型的回复能结合最新知识，时效性强 |
| **无需重新训练** | 不用重新训练或微调大模型，只需更新知识库，成本低、速度快 |

此外，RAG 还具有**可溯源性**：检索到的原文片段可以作为答案的引用来源，就像研究论文中的脚注一样，用户可以对任何说法进行核实，从而建立信任。

## 3. 关键技术详解

### 3.1 数据分段技术

#### 3.1.1 为什么需要数据分段

数据分段（Chunking）是将原始的长文档按一定规则切分成多个较小的、语义相对独立的文本片段的过程。

如果不进行分段处理，会面临以下问题：
- **上下文长度限制**：大模型有最大上下文长度限制（如 8K token），无法一次性处理几十万字的长文档。
- **检索精度低**：整篇文档的向量会被大量无关内容稀释，难以精准匹配用户问题。
- **推理成本高**：送入大模型的 token 数过多，处理慢、费用高。

分段后，系统只需将最相关的几个小片段送入大模型，既突破了上下文限制，又提高了检索精准度，还支持细粒度的来源引用。

#### 3.1.2 分段的设计维度

数据分段的核心是在**"保持语义完整性"**和**"便于精准检索"**之间找到最佳平衡：

- **语义完整性**：确保切分后的块是独立的、意义完整的语义单元。块过大可能包含多个主题引入噪声；块过小则可能割裂关键信息。
- **检索效率与精度**：块是检索的基本单位，需要在"召回相关块"和"避免无关信息"之间取得平衡。
- **上下文边界管理**：块的大小决定了嵌入向量的表征质量和 LLM 处理时的上下文成本。

#### 3.1.3 基础切分方法

| 方法 | 具体操作 | 适用场景 | 注意事项 |
|------|----------|----------|----------|
| 固定大小分块 | 按字符数或词数简单切割 | 结构要求不高的通用文档（如日志） | 可能粗暴切断句子，破坏语义 |
| 按分隔符分块 | 利用段落、标题、句号等自然标记分割 | 结构清晰的文档（Markdown、代码） | 分隔符选择直接影响块质量 |
| 滑动窗口分块 | 在固定大小基础上设置重叠区 | 绝大多数文本的通用改进方案 | 重叠区大小需调优，增加索引量 |
| 多层分块 | 先尝试大分隔符（\n\n），块太大再用小分隔符（\n）递归切分 | 结构复杂的嵌套文档（如 PDF） | 常用且稳健的策略，能在不同层级保持结构 |

本项目采用**多层递归分块 + 滑动窗口**的组合策略，使用 LangChain 提供的 `RecursiveCharacterTextSplitter`，并针对中文优化了分隔符列表。

#### 3.1.4 本项目的分段参数

- **分块大小（chunk_size）**：500 字符。这是语义完整性和检索精度的通用折中值。
- **重叠大小（chunk_overlap）**：80 字符。相邻块之间保留重叠，避免边界处的语义信息被割裂。
- **分隔符优先级**：`\n\n`（段落）→ `\n`（换行）→ `。`（句号）→ `！？`（句末标点）→ `，、`（句中标点）→ 空格 → 字符级兜底。

### 3.2 嵌入模型

#### 3.2.1 什么是嵌入模型

向模型直接输入字符串是不可行的，不便于模型进行计算和文本之间的比较，因此模型的输入必须是数值型向量。

**嵌入（Embedding）**就是将文本字符串经过计算后变为浮点型向量的过程，是自然语言的数字化表示。其基本流程为：
1. **分词（Tokenization）**：将字符串拆分为模型能理解的离散基本单元（Token），每个 Token 映射为一个数字 ID。
2. **嵌入查找（Embedding Lookup）**：通过模型内部的 Embedding Layer（一个巨大的查找表）将每个 ID 转换为稠密的词向量。

#### 3.2.2 嵌入模型与大语言模型的区别

在获得向量序列之后，两类模型的目标和架构导致了路径的分叉：

| 维度 | 嵌入模型 | 大语言模型 |
|------|----------|------------|
| **目标** | 生成代表整段文本语义的、固定长度的向量 | 生成文本（自回归续写） |
| **架构** | 编码器架构（如 BERT） | 解码器架构（如 GPT） |
| **输出** | 通过 CLS 位或池化（平均、最大）综合整个序列信息，输出一个向量 | 基于当前序列计算下一个词元的概率分布，输出文本序列 |
| **用途** | 语义检索、相似度计算、文本聚类 | 对话、写作、翻译、代码生成 |

简单来说：嵌入模型负责"理解语义并压缩成向量"，大语言模型负责"根据上下文生成新文本"。

#### 3.2.3 本项目的嵌入模型选型

本项目选用 **text2vec-base-chinese** 作为嵌入模型，这是一个开源的中文语义向量模型：

- **模型来源**：HuggingFace 社区（shibing624/text2vec-base-chinese）
- **架构**：基于 BERT 的编码器架构
- **输出维度**：768 维稠密向量
- **运行方式**：本地加载运行，数据不出本机，保护隐私
- **优势**：专门针对中文语义优化，向量表征质量高，无需调用外部 API

嵌入模型的关键配置参数：
- `device`：运行设备，本项目使用 CPU（无显卡也可运行）
- `normalize_embeddings`：对输出向量做 L2 归一化，归一化后余弦相似度计算更准确
- `batch_size`：批量编码大小，控制内存占用和处理速度

### 3.3 向量数据库与检索

#### 3.3.1 向量数据库的定义

向量数据库是专为存储和检索高维向量数据设计的数据库系统，通过相似度计算实现高效查询，支撑 RAG 系统的语义搜索能力。

传统关键词检索难以处理语义关联（例如用户问"怎么修电脑"，文档里写的是"计算机故障排查"，关键词不匹配但语义相关），而向量数据库通过嵌入技术将文本映射为向量空间，解决了复杂语义匹配的瓶颈问题。

#### 3.3.2 检索策略

| 检索方式 | 原理 | 适用场景 |
|----------|------|----------|
| 关键词检索 | 在知识库全文匹配用户输入的关键词 | 用户知道确切术语，计算资源消耗低 |
| 向量/语义检索 | 借助嵌入模型计算向量距离，返回语义相似内容 | 语义匹配、跨语言搜索，即使没有确切词汇也能检索 |
| 混合检索 | 同时使用关键词和语义检索，分配权重平衡结果 | 追求最优效果的复杂场景 |

本项目采用**向量语义检索**，通过余弦相似度计算查询向量与知识库向量的相似程度。

#### 3.3.3 相似度计算与 ANN 算法

**相似度度量**：常用余弦相似度，计算两个向量之间的夹角。夹角越小，相似度越高。

**近似最近邻搜索（ANN）**：如果采用精确搜索（暴力遍历所有向量），每次查询都要计算所有片段与问题的距离。当知识库有数千万条时，一次查询可能花费几秒甚至更久。ANN 算法在精度和速度间取得平衡，实现毫秒级检索，代价是可能遗漏极少数本应排在前面的片段，但通常误差在可接受范围内。

主流 ANN 算法：
- **IVF（倒排索引 + 聚类）**：用 K-means 把所有向量分成几百或几千个簇，查询时先找最近的几个簇，只在簇内搜索。
- **HNSW（层次可导航小世界图）**：把向量建成多层图结构，顶层稀疏底层密集，查询时从顶层沿邻居关系快速跳跃到底层。是目前最流行、效果最好的索引方法之一。

#### 3.3.4 本项目的向量数据库选型

本项目选用 **Chroma** 作为向量数据库：

- **定位**：轻量级开源向量数据库，专为 AI 原生嵌入检索设计
- **部署方式**：本地文件持久化存储，无需额外部署服务进程
- **优势**：
  - 开箱即用，Python 接口简洁，与 LangChain 无缝集成
  - 支持持久化存储，数据库保存在本地文件夹
  - 内置余弦相似度检索，支持元数据过滤
  - 适合小型知识库和开发原型，学习成本低

主流向量数据库对比（课件内容）：

| 数据库 | 厂商 | 核心定位 | 部署方式 |
|--------|------|----------|----------|
| Milvus | Zilliz | 开源高性能、可扩展，十亿级向量 | Lite/单机/分布式/云服务 |
| Chroma | Chroma | 轻量级本地向量库，AI 原生 | 本地文件/客户端/云服务 |
| VectorDB | 百度智能云 | 全托管专业向量数据库，百亿向量 | 全托管云服务 |
| Qdrant | Qdrant | 高性能 Rust 实现，过滤能力强 | 本地/分布式/云服务 |

## 4. 系统设计与实现

### 4.1 系统总体架构

本系统采用模块化设计，整体架构分为三层：

```
┌─────────────────────────────────────────────────┐
│                  交互层                           │
│   命令行界面 (chat.py)   网页界面 (app.py)        │
├─────────────────────────────────────────────────┤
│                  核心逻辑层                       │
│   ┌──────────┐  ┌──────────┐  ┌──────────────┐ │
│   │ 文档加载  │→│ 文本分段  │→│ 嵌入向量化    │ │
│   └──────────┘  └──────────┘  └──────┬───────┘ │
│                                       │         │
│   ┌──────────┐  ┌──────────┐  ┌──────▼───────┐ │
│   │ 大模型生成│←│ Prompt拼接│←│ 向量检索      │ │
│   └──────────┘  └──────────┘  └──────────────┘ │
├─────────────────────────────────────────────────┤
│                  数据存储层                       │
│   Chroma 向量数据库   原始文档 (knowledge_base)   │
└─────────────────────────────────────────────────┘
```

系统工作流：
1. **离线流程**：文档加载 → 文本分段 → 嵌入向量化 → 存入 Chroma
2. **在线流程**：用户提问 → 查询向量化 → 语义检索 → Prompt 拼接 → DeepSeek 生成 → 返回答案与来源

**硬件环境：**
- 操作系统：Windows 10/11
- CPU：Intel/AMD 多核处理器
- 内存：8GB 及以上
- 显卡：非必需，CPU 即可运行嵌入模型

**软件环境：**
- Python 3.9 ~ 3.11
- PyCharm 社区版/专业版（开发 IDE）

**核心依赖库：**

| 库名称 | 版本 | 用途 |
|--------|------|------|
| langchain | ≥0.2.0 | 大模型应用开发框架，提供 Chains/Retrieval 组件 |
| langchain-openai | ≥0.1.0 | OpenAI 兼容接口，用于调用 DeepSeek 大模型 |
| langchain-huggingface | ≥0.0.1 | HuggingFace 嵌入模型集成 |
| langchain-community | ≥0.2.0 | 第三方集成（文档加载器、向量库等） |
| chromadb | ≥0.4.0 | Chroma 向量数据库 |
| sentence-transformers | ≥2.2.0 | 嵌入模型运行依赖 |
| pypdf | ≥4.0.0 | PDF 文档解析 |
| python-docx | ≥1.0.0 | Word 文档解析 |
| streamlit | ≥1.30.0 | 网页可视化界面 |

### 4.3 离线建库模块实现

离线建库模块对应 `build_database.py`，包含四个核心步骤：

#### 4.3.1 文档加载

使用 LangChain 的 `DirectoryLoader` 批量加载 `knowledge_base` 文件夹中的所有文档，根据文件扩展名自动选择对应的加载器：

- `.pdf` → `PyPDFLoader`：逐页解析 PDF 文本
- `.txt` → `TextLoader`：纯文本加载
- `.docx` → `UnstructuredWordDocumentLoader`：Word 文档解析
- `.md` → `TextLoader`：Markdown 加载

加载后每个文档片段附带元数据（如来源文件路径、页码），便于后续溯源。

#### 4.3.2 文本分段

使用 `RecursiveCharacterTextSplitter` 进行多层递归分块：

```python
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=80,
    separators=["\n\n", "\n", "。", "！", "？", "，", "、", " ", ""],
)
```

该实现遵循课件中的中文优化分隔符策略，优先按段落和句号等自然语义边界切分，确保每个文本块的语义完整性。

#### 4.3.3 嵌入向量化

使用 `HuggingFaceEmbeddings` 加载 text2vec-base-chinese 模型：

```python
embeddings = HuggingFaceEmbeddings(
    model_name="shibing624/text2vec-base-chinese",
    model_kwargs={"device": "cpu"},
    encode_kwargs={"normalize_embeddings": True},
)
```

模型第一次运行时会自动从 HuggingFace 下载（约 400MB），后续运行直接使用本地缓存。每个 500 字符的文本块被编码为 768 维归一化向量。

#### 4.3.4 向量存储

使用 Chroma 的 `from_documents` 方法一次性完成向量化和存储：

```python
db = Chroma.from_documents(
    split_docs,
    embeddings,
    persist_directory="./vector_db",
)
```

向量数据以本地文件形式持久化保存在 `vector_db` 文件夹中，包含向量索引、原文内容和元数据。

### 4.4 在线问答模块实现

在线问答模块对应 `chat.py`，核心是构建 `RetrievalQA` 问答链。

#### 4.4.1 检索器构建

加载已有的 Chroma 数据库，转换为检索器：

```python
db = Chroma(persist_directory="./vector_db", embedding_function=embeddings)
retriever = db.as_retriever(search_kwargs={"k": 3})
```

检索器默认使用余弦相似度计算，返回与查询向量最相似的前 3 个文本片段。

#### 4.4.2 大模型初始化

通过 LangChain 的 `ChatOpenAI` 类调用 DeepSeek 大模型（DeepSeek 提供 OpenAI 兼容接口）：

```python
llm = ChatOpenAI(
    api_key="your-api-key",
    base_url="https://api.deepseek.com/v1",
    model="deepseek-chat",
    temperature=0.3,
)
```

`temperature=0.3` 表示较低的随机性，使回答更严谨、更贴合原文。

#### 4.4.3 Prompt 模板设计

设计专门的 RAG Prompt 模板，强制模型只根据检索内容回答：

```
你是一个专业的文档问答助手。请严格根据下面提供的【参考资料】来回答用户的问题。
回答规则：
1. 只使用参考资料中的信息，不要编造资料中没有的内容
2. 如果参考资料中没有相关信息，直接回答"根据现有知识库资料，无法回答这个问题"
3. 回答要条理清晰，重点突出

【参考资料】
{context}

【用户问题】
{question}

【你的回答】
```

该 Prompt 是减少幻觉的关键，通过明确的规则约束大模型的生成行为。

#### 4.4.4 RetrievalQA 链组装

将检索器、大模型和 Prompt 组装为完整的问答链：

```python
qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    chain_type="stuff",
    retriever=retriever,
    return_source_documents=True,
    chain_type_kwargs={"prompt": PROMPT},
)
```

- `chain_type="stuff"`：将所有检索片段直接拼接进 Prompt，适合片段数量较少的场景
- `return_source_documents=True`：返回引用的原文片段，实现答案可溯源

调用时只需 `qa_chain.invoke(query)` 即可获得答案和来源。

### 4.5 可视化界面实现

为提升用户体验和演示效果，使用 Streamlit 开发了网页版可视化界面（`app.py`），主要功能包括：

1. **聊天式交互**：类 ChatGPT 的对话界面，支持多轮问答
2. **系统信息展示**：侧边栏显示当前嵌入模型、大模型、检索参数等配置
3. **参考原文展开**：每个回答下方可展开查看检索到的原文片段和来源文件
4. **加载状态提示**：初始化和回答生成时显示加载动画，提升交互体验
5. **聊天历史保持**：页面刷新前保留对话历史

运行命令：`streamlit run app.py`，启动后浏览器自动打开，默认地址为 `http://localhost:8501`。

### 5.4 参数对比实验

为验证关键参数对系统效果的影响，设计了两组对比实验。

#### 实验一：不同分块大小（chunk_size）对检索效果的影响

固定 `top_k=3`，测试不同 chunk_size 下的回答质量：

| chunk_size | 分块数量 | 平均检索相关度 | 回答完整性 | 问题 |
|------------|----------|----------------|------------|------|
| 200 | 约 550 | 高（小块语义集中） | 较低（单块信息不足） | 上下文不够，回答不完整 |
| **500** | **约 220** | **较高** | **高** | **平衡最佳，推荐使用** |
| 800 | 约 140 | 中（大块含多主题） | 高 | 引入噪声，检索精度下降 |
| 1500 | 约 75 | 低（大块稀释严重） | 较高 | 无关内容多，干扰大模型 |

**结论**：chunk_size=500 时在检索精度和回答完整性之间取得最佳平衡，与课件中的建议一致。块过小导致信息不足，块过大引入噪声。

#### 实验二：不同检索数量（top_k）对回答效果的影响

固定 `chunk_size=500`，测试不同 top_k 的效果：

| top_k | 检索片段数 | 回答准确度 | 推理速度 | 问题 |
|-------|------------|------------|----------|------|
| 1 | 1 | 较低（信息不全） | 快 | 单个片段可能不包含完整答案 |
| **3** | **3** | **高** | **较快** | **信息充足且噪声少，推荐** |
| 5 | 5 | 高 | 中等 | 信息冗余，部分片段无关 |
| 10 | 10 | 中 | 慢 | 大量无关内容干扰，可能超出上下文 |

**结论**：top_k=3 时效果最佳，既能提供充足的上下文信息，又不会引入过多噪声。检索数量过多反而会降低回答质量并增加推理成本。

## 6. 总结与展望

### 6.1 项目总结

本项目基于课程讲授的 RAG 技术原理和 LangChain 框架，完整设计并实现了一个知识库智能问答系统。主要完成了以下工作：

1. **理论学习**：深入学习了 RAG 的核心原理，包括大模型局限性、数据分段、嵌入模型、向量数据库与检索等关键技术。
2. **系统实现**：基于 LangChain + Chroma + DeepSeek + text2vec 技术栈，实现了从文档加载、文本分段、向量化存储到检索问答的完整流程。
3. **功能完善**：提供了命令行和网页版两种交互方式，支持多格式文档、中文优化分段、答案溯源等功能。
4. **实验验证**：通过问答测试和参数对比实验，验证了系统的有效性，并确定了最优参数配置（chunk_size=500, top_k=3）。

系统能够有效解决大模型的知识截止和幻觉问题，回答准确、可溯源，达到了课程实训的预期目标。

### 6.2 不足与展望

当前系统仍存在一些可改进的方向：

1. **检索策略优化**：目前仅使用纯向量语义检索，未来可引入关键词检索与语义检索结合的混合检索策略，进一步提升召回率。
2. **重排序（Rerank）**：在检索后增加重排序模型，对初步检索结果进行精排，提高最相关片段的排名。
3. **多轮对话记忆**：引入 LangChain 的 Memory 模块，让系统支持带上下文的多轮对话，理解指代和省略。
4. **文档上传功能**：在网页界面增加文档上传和实时建库功能，用户可动态添加新知识。
5. **嵌入模型升级**：尝试更大规模的中文嵌入模型（如 text2vec-large-chinese、bge-large-zh），提升向量表征质量。
6. **知识库管理**：增加知识库的增删改查管理界面，支持文档版本管理。
